# Сеть: гость, туннели, P2P

## Что сделано (M1)

- **Сеть гостя — собственный NAT в агенте** (`agent/`, `GuestNetwork`). Сетевая карта VM —
  `VZFileHandleNetworkDeviceAttachment`, один конец socketpair. Всё остальное делает процесс агента:
  DHCP, DNS, NAT для TCP, UDP и ICMP. Root, pf и NetworkExtension не нужны.
  - Гостю доступен только интернет. Роутер, LAN- и VPN-адреса хоста, шлюз, CGNAT и link-local недоступны.
    Проверка — в `agent/README.md`.
  - К порту simstream `:7300` агент подключается через loopback-проброс внутри себя.
  - Трафик всё ещё выходит с IP владельца (см. ниже).
- **Удалённый симулятор — WebRTC P2P.** Браузер ⇄ мак владельца напрямую. Наш сервер передаёт только
  сигнализацию (несколько килобайт на сессию) и выдаёт временные учётные данные TURN. Когда пробить NAT
  не удаётся (обычно в 10–20% случаев), трафик идёт через наш coturn.
- **CI туннеля не требует.** Раннер в госте сам ходит в GitHub, входящих соединений нет.

## IP владельца: варианты на будущее

Зачем изначально задумывалась exit-нода:
1. Гость не должен видеть домашнюю сеть. Уже решено агентом, туннель для этого не нужен.
2. Трафик не должен идти с домашнего IP хоста, иначе абьюз задачи ложится на владельца.
3. Контроль, куда задача может ходить.

**Вариант А — белый список с мака хоста (для open source).** Гостю даём не сеть, а HTTP(S)-прокси через vsock,
который пускает только к разрешённым адресам: GitHub, реестры SPM, CocoaPods, npm, CDN Apple. Наш сервер
не на пути трафика, WireGuard не нужен.
- Минус: трафик идёт с IP хоста. Белый список делает абьюз почти невозможным.
- Минус: инструменты, которые игнорируют `HTTPS_PROXY` (например, `git` по SSH), работать не будут.

**Вариант Б — выход через сеть компании (для private pool).** Компания поднимает у себя WireGuard-эндпоинт
или наш маленький exit-бинарь, мак строит туннель туда, наш сервер только раздаёт одноразовые ключи. Бонус:
сборки получают доступ к внутренним ресурсам компании, к приватным реестрам и артефактам.

**Вариант В — свои exit-ноды (для маркетплейса).** Linux с ядерным WireGuard, nftables (NAT и фильтр) и DNS.
Агент — тупая труба для пакетов: кадры гостя → снять Ethernet → WireGuard/UDP → exit-нода. На каждую задачу
одноразовые ключи, сервер регистрирует пира на ноде с адресом `/32`.
- WireGuard на стороне мака: готовой Swift-библиотеки нет. Варианты:
  - свой клиент на CryptoKit (X25519 и ChaCha20-Poly1305 есть; BLAKE2s, HKDF и HChaCha20 дописывать;
    протокол Noise IKpsk2, таймеры, окно повторов) — 1,5–3 тыс. строк;
  - wireguard-go как статическая библиотека через C API, как в официальном WireGuardKit.
- Туннель **не защищает данные арендатора от хоста**: кадры проходят через агент до шифрования. Его задачи —
  пустить на exit-ноду только наши ноды и защитить трафик от провайдера.
- MTU 1420 через DHCP option 26, только IPv4, DNS на exit-ноде.

**Вариант Г — P2P VPN в стиле Tailscale.** Тоже нужны координатор, STUN и relay. Для CI на второй стороне
никого нет, так что смысла мало. Для симулятора P2P уже даёт WebRTC (ниже).

## Идея: трафик симулятора через машину разработчика

В интерактивной сессии у второй стороны есть машина. Сетевой трафик приложения в симуляторе можно завернуть
обратно к разработчику по тому же P2P-каналу (канал данных WebRTC или туннель). Тогда:
- приложение выходит в интернет с IP разработчика, а не с IP хоста, и вопрос абьюза снимается;
- приложение видит `localhost` разработчика: dev-сервер, Metro, моки API.

Пожалуй, это самая сильная фича удалённого симулятора. В M1 не делали.

## P2P: WebRTC против VPN

| | WebRTC | P2P VPN (WireGuard) |
|---|---|---|
| Что передаёт | только наши потоки: видео и каналы данных | любой IP-трафик: SSH, отладчик, файлы |
| Видео | контроль перегрузки, рассчитанный на видео в реальном времени | наш TCP поверх туннеля, при потерях задержка скачет |
| Клиент | обычное приложение или браузер | системное расширение VPN и разрешение пользователя |
| Обход NAT | готовый | самим или Tailscale |

Для симулятора выбран WebRTC. На стороне мака — libdatachannel (`simstream/SimStreamPeer`), на стороне
клиента — браузер. VPN понадобится, только если захотим отдавать «полноценную машину в сети».
