# M1 / D: P2P-транспорт, simstream и Viewer

Сначала прочитай `docs/contracts.md` (общие правила, владельцы папок, блокировка VM) и `docs/roadmap.md`.
Твои папки: `simstream/`, `viewer/`, `protocol/Sources/SimStreamProtocol/`. Worktree: `../maccheri-d`,
ветка `task/transport`.

## Цель

Удалённый симулятор через интернет: viewer и мак владельца соединяются напрямую (P2P), через наш
сервер идут только сигнализация и, если пробиться не удалось, TURN. Viewer становится продуктом:
вход, сессии, базовые возможности устройства.

## Что есть

- `simstream` (сервер в госте, TCP :7300), `SimStreamClient`, `simstream-bench`, Maccheri Viewer.
  Задержка клик → кадр в локальной сети 22–26 мс p50 (`bench/simstream/RESULTS.md`, `simstream/README.md`).
- Решение по транспорту: склоняемся к WebRTC (см. `docs/roadmap.md`). Пользователь думает о P2P VPN.
  Первым делом сделай короткое исследование и замер (ниже), а не только код.

## Что сделать

1. **Выбор схемы WebRTC (замер, потом решение):**
   - где живёт WebRTC-пир на стороне мака: на хосте (библиотека `HostPeer`, которую вызывает агент A;
     она соединяется с simstream в госте по TCP) или прямо в госте. Рекомендация — хост: там
     учётные данные TURN и нет двойного NAT vmnet;
   - как везти видео:
     - (a) готовый H.264 из simstream в видеодорожке WebRTC без перекодирования
       (passthrough-кодер или кодер в стеке WebRTC);
     - (b) наши сообщения SimStream через RTCDataChannel (ненадёжный неупорядоченный для видео,
       надёжный для касаний).

     Сравни задержку и поведение при потерях: `simstream-bench` через сеть с потерями и задержкой
     (Network Link Conditioner или `dnctl`/`pfctl` на хосте), 1–3% потерь, RTT 50 мс;
   - библиотека: Google WebRTC для macOS через SwiftPM (готовый xcframework) или аналог. Скачать
     можно, это мелкая зависимость;
   - итог запиши в `simstream/README.md` с цифрами.
2. **`HostPeer` по контракту** (`docs/contracts.md`, стык A ↔ D):
   - подключается к сигнализации B с ролью host, создаёт offer, берёт `iceServers` из `SignalingInfo`;
   - получает поток от гостя через `connectToGuest`;
   - выходит по bye, отключению или таймауту.

   Пока A не готов, проверяй через свой тестовый CLI, который сам поднимает `HostPeer`.
3. **Viewer:**
   - вход: URL control plane и инвайт → токен в Keychain;
   - «Новая сессия» (выбор устройства из `HostInfo.capacity.devices`), ожидание `ready`,
     сигнализация с ролью viewer, P2P;
   - оверлей статистики: тип соединения (прямое или через TURN), RTT, задержка клик → кадр;
   - кнопка «Завершить» (DELETE и bye). Режим прямого подключения `host:port` для разработки оставить.
4. **Возможности устройства** (сервер simstream и viewer):
   - клавиатура: Indigo keyboard, см. экспорт `IndigoHIDMessageForKeyboardArbitrary`
     и `…KeyboardNSEvent` в SimulatorKit;
   - кнопка Home или свайп Home, блокировка экрана;
   - поворот экрана;
   - установка своего `.app`: перетаскивание в окно → передача по каналу данных → `simctl install` и запуск.
5. Тесты: протокол и сигнализация (с фейковым сервером), `LatencyTracker`, сериализация новых сообщений.

## Готово, когда

- Со второго мака из другой сети (хотспот телефона) viewer входит, создаёт сессию и работает
  с симулятором через сервер B. Сначала можно на локальном control plane плюс тестовый CLI
  вместо агента, потом с настоящим A.
- Задержка клик → кадр через интернет и тип соединения видны в оверлее, цифры записаны
  в `bench/simstream/RESULTS.md`.
- Клавиатура, Home, поворот и установка `.app` работают.

## Не делать

Браузерный клиент (держи в уме: WebRTC его позволит), звук, мультитач, подпись и нотаризацию.
