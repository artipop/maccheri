# Модель угроз

Защищать надо в обе стороны: владельца мака от арендатора и арендатора от владельца. Первое решается, второе —
фундаментально нет.

## Владелец ← арендатор (решается)

- **Изоляция VM.** Код арендатора работает только внутри VM на Virtualization.framework. Без проброса USB
  и без общих папок на запись: общая папка с заданием доступна гостю только для чтения.
- **Изоляция сети важнее самой VM.** Гость не должен видеть домашнюю сеть: роутер, NAS, другие машины,
  сам хост. Сделано: собственная NAT-сеть в агенте (`VZFileHandleNetworkDeviceAttachment`), гостю доступен
  только интернет. Проверка изнутри гостя — в `agent/README.md`.
- **IP владельца.** Исходящий трафик задачи идёт с домашнего IP владельца. Если задача будет рассылать спам
  или атаковать, отвечать придётся ему. Варианты — в `networking.md`: белый список адресов для open source,
  выход через сеть компании для private pool, exit-ноды для маркетплейса.
- **Ресурсы.** Лимиты CPU, RAM и диска, расписание («только ночью»), пауза в строке меню.
- **Эфемерность.** Каждая задача — чистый APFS-клон базового образа, после задачи клон удаляется.
  Осиротевшие клоны агент удаляет при старте.

## Арендатор ← владелец (фундаментально не решается)

У владельца физический доступ и root: он может прочитать диск и память VM. Аналога AMD SEV или Intel TDX
(confidential computing) для сторонних разработчиков на маках нет. Внутри Private Cloud Compute у Apple
похожее есть, но оно закрыто.

**Шифрование и удалённая ФС не помогают.** Компилятору нужны данные в открытом виде, значит в какой-то
момент они окажутся расшифрованными в памяти VM, а это память процесса на хосте. Ключ расшифровки придётся
отдать внутрь VM, и хост может его перехватить. И главное: хост может написать свой «агент», который говорит
по нашему протоколу и просто сохраняет исходники. Доказать, что на той стороне работает наш неизменённый
бинарь, нечем.

**Целостность хуже утечки.** Злонамеренный хост может:
- соврать «тесты прошли»;
- внедрить бэкдор в собранный бинарь. Если мы его подпишем и отправим в App Store, получится атака
  на цепочку поставки;
- для edge-сценариев — подменять ответы пользователям (поэтому edge не делаем, см. `product.md`).

**Что можно сделать:**
- **Подпись только на доверенной стороне.** Хост собирает неподписанный `.xcarchive`. Сертификаты и ключи
  App Store Connect на ноды не попадают никогда.
- **Секреты не передаются в задачу.** Шаги с секретами выполняются на доверенной стороне.
- **Сегменты, где утечка не страшна:** open source, PR-проверки, тесты без секретов. Private pool, где доверие
  решается организационно.
- **Двойная сборка** на двух независимых хостах со сравнением. Xcode-сборки при этом не гарантированно побитово
  воспроизводимы, так что это вспомогательная мера.
- **Обнаружение вместо предотвращения:**
  - canary-токены и фейковые ключи в проектах, задачи-ловушки для проверки хостов;
  - KYC, депозит или договор с хостом, рейтинг;
  - выборочное дублирование CI-задач.
- **Managed Device Attestation через MDM** (macOS 14+): Apple подписывает факт, что включены SIP и Full Security.
  Порог это поднимает, но злонамеренного агента, подписанного своим сертификатом, не отсекает, а MDM на личном
  маке — большой барьер. Детали надо проверять.

**Принцип:** продукт строим так, чтобы утечка была не критична, а не так, чтобы её не было.

## Удалённый симулятор

- Хост видит загруженный `.app` и всё, что показывает симулятор. Утечка бинаря менее критична, чем исходников,
  но для закрытых приложений это всё равно утечка.
- Сигнализация WebRTC идёт через наш сервер, медиа — P2P с шифрованием DTLS-SRTP. Сервер видео не видит,
  хост видит всё.
- Токены сигнализации одноразовые, по ролям и на одну сессию. В логи сервера они не пишутся.

## Мини-прод (M1)

Пользователей нет, доступ по одному общему секрету (`MACCHERI_SHARED_TOKEN`). Хост получает свой `agentToken`
при регистрации. Это годится только для своей команды. Перед любым внешним доступом нужны аккаунты
(инвайты в коде уже есть).
