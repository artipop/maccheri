# simstream: удалённый симулятор iOS

Симулятор работает в macOS-госте, его экран идёт видеопотоком к пользователю, клики и клавиши
оттуда превращаются в касания и нажатия.

Основной путь — через интернет, в браузер (раздел «Через интернет: WebRTC»):

```
браузер (web/) ⇄ WebRTC (P2P или TURN) ⇄ HostPeer (агент на хосте) ──TCP──▶ simstream (гость, :7300) ──▶ симулятор
                └──── сигнализация через control plane ────┘
```

Путь для замеров в локальной сети, без WebRTC:

```
viewer (второй Mac) ──TCP──▶ maccheri-vm --forward (хост, *:7300) ──vmnet NAT──▶ simstream (гость, :7300) ──▶ симулятор
```

| Что | Где |
|---|---|
| Протокол: сообщения с префиксом длины, тесты | `protocol/Sources/SimStreamProtocol` |
| WebRTC на стороне мака: `HostPeer`, обёртка libdatachannel | `simstream/Sources/SimStreamPeer` |
| Тестовый агент: `HostPeer` без A, enroll, heartbeat, `/agent/v1/work` | `simstream/Sources/simstream-peer` |
| Веб-клиент, dev-мок control plane, замеры в браузерах | `web/` (см. `web/README.md`) |
| Приватные API CoreSimulator и SimulatorKit (захват экрана, касания) | `simstream/Sources/SimulatorBridge` |
| Сервер `simstream` (гость) | `simstream/Sources/simstream` |
| Клиент: сеть, декодирование, задержка клик → кадр | `simstream/Sources/SimStreamClient` |
| Безоконный клиент для замеров | `simstream/Sources/simstream-bench` |
| Проброс порта с хоста в гостя | `agent/Sources/AgentCore/TCPForwarder.swift`, `maccheri-vm --forward` |
| Просмотрщик | `viewer/` |

## Запуск

На маке с VM (одновременно может работать только одна VM):

```sh
# 1. VM с пробросом порта. Если гость уже работает, вторую VM не запускать, а только пробросить порт:
agent/scripts/build.sh
maccheri-vm --images /Volumes/Dev/vm/images --work /Volumes/Dev/vm/work \
    --image macos-27-xcode-27.2 --timeout 28800 --forward 7300
#   или для уже работающего гостя:
maccheri-vm --attach 192.168.64.5 --forward 7300

# 2. simstream в госте: собрать, скопировать, загрузить симулятор из ~/udid, открыть приложение
simstream/scripts/run-in-guest.sh 192.168.64.5 dev.maccheri.tapprobe
#   опции сервера после --:  … -- --scale 1 --fps-cap 60 --bitrate 16000 --refine 3
```

На втором маке открыть `MaccheriViewer.app` (см. `viewer/README.md`) и подключиться
к `Mac-mini-Artem.local:7300`.

Замер без окна: TapProbe на переднем плане, затем

```sh
swift run -c release --package-path simstream simstream-bench --host 127.0.0.1 --taps 100
swift run -c release --package-path simstream simstream-bench --host … --tap 0.5,0.49     # один тап
swift run -c release --package-path simstream simstream-bench --host … --drag 0.5,0.8,0.3 # свайп
```

## Как это работает

- **Захват.** `SimScreen` регистрирует колбэки экрана устройства. Кадр приходит только
  при изменении, в простое нет ни кадров, ни трафика. Если после регистрации поверхность не появилась
  за 2 с, регистрация повторяется, потом перебираются screenID. Так лечится «первый запуск
  после загрузки симулятора без кадров».
- **Кодирование.** IOSurface сразу копируется с конвертацией (`VTPixelTransferSession`,
  BGRA → NV12). По умолчанию в полном разрешении, 1206×2622: на половинном (`--scale 0.5`) текст
  заметно мылится, а выигрыш около 6 мс. Дальше H.264 через VideoToolbox: low-latency rate control,
  `RealTime`, без переупорядочивания кадров. Частота ограничена `--fps-cap`: изменение,
  пришедшее раньше интервала, кодируется по его истечении. Ключевые кадры отправляются при подключении,
  по `requestKeyframe` и раз в 5 с.
- **Дошлифовка в простое.** Low-latency rate control тратит на один кадр мало бит, и последний
  кадр после изменения (или ключевой кадр при подключении) получается мыльным. Когда экран
  и ввод 150 мс стоят, тот же кадр кодируется ещё `--refine` раз (по умолчанию 3), с шагом 60 мс.
  На задержку клик → кадр это не влияет в пределах шума (см. RESULTS).
- **Касания.** `began`, `moved` и `ended` превращаются в mouse down, dragged и up через
  `IndigoHIDMessageForMouseNSEvent` (шестиаргументная сигнатура Xcode 27, см. комментарий в
  `PrivateAPI.swift`). Перемещения чаще 17 мс сервер склеивает и отправляет последнее, потому что Indigo
  сам отбрасывает те, что приходят чаще 16 мс.
- **Задержка.** Каждый кадр несёт `inputAck`, id последнего касания, которое симулятор принял
  к моменту захвата. Клиент считает время от отправки `began` до декодирования первого кадра с
  `inputAck ≥ id`. Синхронизировать часы не нужно. `ackAgeMicros` показывает серверную часть
  этого времени.
  Ограничение: ack означает «симулятор принял касание», а не «приложение перерисовалось». Если в этот
  момент на экране шла анимация, кадр с ack может прийти раньше ответа, и задержка выйдет
  заниженной. `simstream-bench` поэтому меряет ещё и по смене пикселя в центре (TapProbe): обе
  цифры совпадают.
- **Сеть.** Один TCP-поток, `TCP_NODELAY`. Одновременно работает один клиент, новое подключение
  вытесняет старое. Если в сокете скопилось больше 512 КБ, кадры выбрасываются, а следующий отправляется
  ключевым. Авторизации нет: только локальная сеть.

## Через интернет: WebRTC

### Где пир и на чём

Пир на стороне мака работает **на хосте**, в `HostPeer` (библиотека `SimStreamPeer`, её вызывает агент A).
До гостя он ходит обычным SimStream по TCP (`connectToGuest`). Учётные данные TURN остаются на
хосте, и у WebRTC нет второго NAT vmnet. Гость про WebRTC ничего не знает.

Стек WebRTC — **libdatachannel** v0.24 (C API) с Mbed TLS 3.6, собран статически:
`scripts/build-libdatachannel.sh` кладёт `Vendor/LibDataChannel.xcframework` (5,4 МБ, лежит в git,
чтобы агент собирался без cmake). Почему не Google WebRTC: нам не нужны его захват, кодеки и
аудио, а готовый H.264 из гостя надо везти без перекодирования. В libdatachannel для этого есть
упаковщик H.264 в RTP, ответ на NACK и обработка PLI, а также SCTP-каналы данных (usrsctp),
ICE (libjuice) и DTLS-SRTP. Всё это стандартный WebRTC, браузерам плагины не нужны.

### Что в offer

Offer создаёт хост (контракт), в нём три вещи:

| | Что везёт | Надёжность |
|---|---|---|
| канал `control` | всё, кроме видео: касания, клавиши, кнопки, поворот, установка `.app`, ping, `hello`, `FrameInfo` | надёжный, упорядоченный |
| канал `video` | видео кусками `VideoChunk` по 16 КБ (режим b) | упорядоченный, повторы до 200 мс |
| дорожка H.264 | видео RTP, payload type по ответу браузера, `playout-delay` 0/0 (режим a) | NACK, PLI |

Сообщения в каналах — те же SimStream без префикса длины (`encodedBody()`). Браузер сразу после
открытия `control` выбирает режим (`StreamConfig`), и до этого видео не идёт. Хост просит
у гостя ключевой кадр и дальше гонит видео только выбранным путём.

- **(a) Дорожка.** Кадр гостя (AVCC, плюс SPS/PPS на ключевых) уходит в упаковщик как есть, RTP timestamp —
  время захвата в госте (90 кГц). Браузер показывает её в `<video>`, `jitterBufferTarget = 0`. Метаданные кадра
  (`inputAck`) приходят в `FrameInfo` по `control` и сопоставляются по RTP timestamp
  в `requestVideoFrameCallback`.
- **(b) Канал данных.** Кадр режется на куски, браузер собирает их и декодирует WebCodecs
  (`optimizeForLatency`), а потом рисует в `<canvas>`. Джиттер-буфера нет совсем.

В обоих режимах задержка клик → кадр меряется одинаково: момент, когда кадр уходит на экран
(rVFC для `<video>`, следующий `requestAnimationFrame` после отрисовки для canvas). Цифры по
браузерам — в `bench/simstream/RESULTS.md`. По умолчанию везде (a): это стандартный путь
с восстановлением потерь. Окончательный выбор сделаем по замерам через интернет, в разных сетях
и с потерями. Для замеров (b) включается параметром `?video=dataChannel` или кнопкой «Видео: …»
на панели прямо в сессии, без переподключения. Без WebCodecs (не secure context) остаётся только (a).

### Скорость и потери

Встроенного управления скоростью (GCC/TWCC, как в Google WebRTC) у libdatachannel нет, и на хосте
мы видео не перекодируем. Поэтому:

- **Скорость задаёт гость.** VideoToolbox в режиме low-latency с потолком `--bitrate` (16 Мбит/с).
  Кадры идут только при изменении экрана: в простое трафика нет, при непрерывной прокрутке на полном разрешении
  выходит около 1,4 Мбит/с (RESULTS), ключевой кадр весит порядка 100 КБ. Пиков выше потолка нет,
  но и подстройки под узкий канал нет.
- **(a) Потери.** Браузер шлёт NACK, хост повторяет пакеты из истории (1024 пакета). Если кадр
  не восстановился, браузер шлёт PLI, и хост просит у гостя ключевой кадр (не чаще раза в 100 мс).
  Пейсинга нет: ключевой кадр уходит пачкой со скоростью линии, и на узком канале или TURN
  это само по себе может дать потери.
- **(b) Потери и перегрузка.** SCTP повторяет куски до 200 мс. Его управление перегрузкой (как у TCP)
  и есть наше управление скоростью: при потерях окно сжимается. Если в канале скопилось больше
  1 МБ, хост выбрасывает кадры до следующего ключевого и просит его у гостя. Браузер замечает дыру
  в номерах кадров (или недостающий кусок) и тоже просит ключевой кадр, не чаще раза в 300 мс,
  пока он не придёт.
- **Дальше (не M1).** Нужна петля адаптации. Браузер раз в секунду отправляет по `control` потери,
  RTT и пропускную способность из `getStats`, а хост просит гостя сменить битрейт или масштаб
  (новое сообщение и перенастройка кодера без переподключения). В режиме (a) можно ещё брать
  REMB от браузера (`rtcChainRembHandler`).

### Конец сессии

`run()` возвращается, когда зритель прислал `bye`, когда соединение пропало и не восстановилось
за 10 с, когда зритель не подключился за 120 с или когда вызвали `stop(reason:)` (или отменили задачу).
Если отваливается гость, `run()` бросает ошибку. Сигнализация после установки соединения уже не нужна:
если сервер сигнализации пропал, сессия продолжается.

### Возможности устройства

| Что | Как в госте | В браузере |
|---|---|---|
| Касания | `IndigoHIDMessageForMouseNSEvent` | Pointer Events, мышь и тач |
| Клавиатура | `IndigoHIDMessageForKeyboardArbitrary`, USB HID usage | `KeyboardEvent.code` → usage (`web/src/keyboard.ts`) |
| Home, блокировка | `IndigoHIDMessageForButton` (source 0 и 1, target 0x33) | кнопки на панели |
| Поворот | GSEvent «смена ориентации» в `PurpleWorkspacePort` устройства | ⟲ ⟳ на панели |
| Установка `.app` | zip по `control` → `ditto -x -k` → `simctl install` → `simctl launch` | перетащить zip в окно или «Установить .app» |

- **Клавиатура** передаёт физические клавиши, а не символы, как настоящая аппаратная клавиатура.
  Раскладку выбирает iOS. В симуляторе с русской раскладкой `hello` печатается как `руддщ`:
  это не ошибка, а раскладка устройства.
- **Поворот.** Фреймбуфер симулятора при повороте остаётся портретным, содержимое поворачивается
  внутри него. Клиент поворачивает картинку обратно (CSS) и пересчитывает касания. Домашний
  экран iPhone не поворачивается, поэтому там картинка ляжет боком, как на настоящем телефоне.
- **Блокировка.** На заблокированном устройстве дисплей гаснет и кадров нет, поэтому в браузере
  остаётся последний кадр. Разблокировка — кнопкой Home.
- Отладка кнопок: `simstream --udid … --debug-button <source>[:<target>[:<page>]]` (hex) нажимает
  одну кнопку и выходит.

### Как проверить без агента и control plane

```sh
xcrun simctl boot <UDID>                                    # симулятор хоста: приватные API те же, что в госте
swift build -c release --package-path simstream
simstream/.build/release/simstream --udid <UDID> &          # :7300
(cd web && npm install && npm run dev) &                    # клиент + мок control plane на :5173
simstream/.build/release/simstream-peer --guest 127.0.0.1:7300 --control-plane http://localhost:5173 --shared-token dev
open http://localhost:5173/                                 # вход: токен dev
```

С настоящим control plane вместо мока: `--control-plane https://… --shared-token $MACCHERI_SHARED_TOKEN`.
Замеры и проверки в браузерах — `web/bench/latency.mjs` (см. `web/README.md`).

## Нюансы гостя

- Бинарник в госте нельзя перезаписывать на месте: ядро убьёт запущенный процесс за невалидную
  подпись (`Code Signature Invalid`). Копировать во временный файл и делать `mv`, как в `run-in-guest.sh`.
- Аппаратного скейлера в госте нет (`IOServiceMatching failed for AppleM2ScalerParavirtDriver`),
  копирование и конвертация идут без него, около 2 мс на половинном разрешении и около 4 мс
  на полном.
- Чёрный экран на 1–3,5 с при холодном запуске приложения (Safari, Карты, Календарь) рисует сам
  симулятор в госте: исходная IOSurface чёрная, `simctl io screenshot` в этот момент тоже показывает
  чёрное. К потоку это отношения не имеет. Проверка: `SIMSTREAM_TRACE=1` пишет в лог переходы
  `source surface BLANK/ok`, а `simstream-bench --soak 60` считает чёрные декодированные кадры.
- Приватные API привязаны к Xcode 27.2. При обновлении Xcode проверить сигнатуры
  в `SimulatorBridge/PrivateAPI.swift`.
