# Веб-клиент Maccheri

Удалённый симулятор iOS в браузере: вход через GitHub, команды и их маки, выбор устройства,
«Новая сессия», экран
симулятора по WebRTC, касания, клавиатура, Home, блокировка, поворот, установка `.app`.
Работает в актуальных Chrome, Safari и Firefox на любой ОС.

Vite и ванильный TypeScript, без фреймворка и без зависимостей в рантайме. Сборка — один
`index.html` с бандлом (около 30 КБ), без серверного рендеринга и с относительными путями. Так клиент
потом можно встроить в webview VS Code или в нативную обёртку.

| Файл | Что |
|---|---|
| `src/api.ts` | типы и вызовы control plane, повторяют `MaccheriProtocol` |
| `src/protocol.ts` | сообщения SimStream (повторяют `SimStreamProtocol`), сборка кадров из кусков |
| `src/session.ts` | сигнализация с ролью viewer, `RTCPeerConnection`, каналы, статистика |
| `src/video.ts` | показ видео: `<video>` для дорожки, WebCodecs и `<canvas>` для канала данных |
| `src/latency.ts` | задержка клик → кадр (как `LatencyTracker` в Swift) |
| `src/keyboard.ts` | `KeyboardEvent.code` → USB HID usage |
| `src/main.ts` | экраны: вход, команда (маки, участники, приглашения, GitHub), ожидание, сессия, оверлей |
| `dev/mock-control-plane.ts` | control plane в памяти внутри dev-сервера Vite |
| `bench/latency.mjs` | замер клик → кадр и проверки в настоящих браузерах |

## Разработка

```sh
npm install
npm run dev          # http://localhost:5173 и мок control plane на том же порту
npm test             # vitest: протокол, задержка, клавиатура, типы API по фикстурам control plane
npm run build        # → dist/, его раздаёт control plane (PUBLIC_DIR)
```

Для других машин в LAN и для Firefox нужен https. WebCodecs есть только в secure context, а Firefox
со страницы `http://localhost` не устанавливает ICE. Поэтому с самоподписанным сертификатом:
`DEV_HTTPS_CERT=dev.crt DEV_HTTPS_KEY=dev.key npm run dev`, хост — `simstream-peer … --control-plane https://<IP>:5173 --insecure`.
Сертификат: `openssl req -x509 -newkey rsa:2048 -nodes -days 30 -subj /CN=dev -addext "subjectAltName=IP:<IP>" -keyout dev.key -out dev.crt`.

Мок нужен, пока нет настоящего control plane, и для работы без него. По умолчанию он изображает
аккаунты v2. Кнопка «Войти через GitHub» ведёт на его страницу-заглушку, где вводится любой логин.
Логин `dev` — владелец команды «Dev» с маком `simstream-peer`, остальные логины начинают без
команды. Кроме входа мок умеет команды, участников, приглашения, коды для маков и «установку»
GitHub App. С `MOCK_ACCOUNTS=v1` мок ведёт себя как v1: принимает любой код приглашения, а пути
`/auth/*` отвечают 404. В обоих режимах работают общий токен `dev` (`MOCK_SHARED_TOKEN`) как
bearer, `enroll` (с токеном или с кодом команды), `heartbeat`, `/agent/v1/work` и сигнализация.
Хост для мока — `simstream-peer` (см. `simstream/README.md`, «Как проверить без агента»).
ICE-серверы мока задаёт `MOCK_ICE="stun:…,turn:user:pass@host:3478"`.

Клиент против настоящего control plane:
- `VITE_API=http://localhost:8080 npm run dev`: dev-сервер проксирует туда `/v1`, `/agent`, `/auth` и `/github`, мок выключен;
- либо `?api=https://maccheri.example` в адресе открытой страницы: адрес запоминается в `localStorage`,
  а сбрасывается через `?api=`.

## Вход и команды

Какой вход показать, клиент решает сам (`home()` в `src/main.ts`):

- **v2** (control plane на Go, `Teams.swift`). Если `/auth/github/login` отвечает редиректом,
  показывается «Войти через GitHub». Дальше браузер сам носит cookie `maccheri_session`, запросы идут
  с `credentials: 'same-origin'`, а изменяющие — ещё и с `X-Maccheri-CSRF: 1`. Выход — `POST /auth/logout`.
  После входа клиент показывает команду: её маки и «Новую сессию» с `teamID`, участников. Админам и
  владельцам доступны «Пригласить» (ссылка с ролью), «Добавить мак» (одноразовый код для
  Maccheri.app) и «Подключить GitHub» со списком установок. Если команд несколько, их переключает
  список в шапке; там же пункт «Новая команда…». Пользователь без команды видит форму «Создать
  команду» и подсказку открыть приглашение.
- **v1** (Vapor, мини-прод). Если `/auth/github/login` отвечает 404 или отдаёт саму страницу (catch-all
  Vapor), показывается прежняя форма. Поле принимает код приглашения или общий токен команды. Если
  `/v1/auth/redeem` отвечает 404 (мини-прод без пользователей), введённое значение считается
  токеном. Токен хранится в `localStorage` и уходит в `Authorization: Bearer`. Если токен уже есть,
  клиент сразу работает как v1.

Приглашение `https://<домен>/invite/<код>` (`Invite.url`) скрипт в `index.html` до загрузки бандла
переписывает в `/?invite=<код>`: пути к ассетам относительные и из `/invite/` не загрузились бы.
Если пользователь не вошёл, он уходит на GitHub с `return_to` на эту же ссылку. После входа клиент
вызывает `POST /v1/invites/{код}/accept` и открывает команду. Серверу достаточно отдавать
`index.html` на `/invite/*`, как это уже делает catch-all.

Другие параметры адреса: `?video=dataChannel` — видео по каналу данных и WebCodecs вместо дорожки
(по умолчанию дорожка; в сессии переключается кнопкой «Видео: …»), `?relay=1` — только через TURN,
`?invite=…` или `?token=…` — заполнить поле входа.

## Тесты типов API

`test/api.test.ts` сверяет типы из `src/api.ts` с JSON-фикстурами control plane
(`controlplane/Tests/Fixtures`, их генерирует B из `MaccheriProtocol`). Проверяются обязательные
поля, лишние поля, UUID и даты. Если фикстур рядом нет, тест пропускается. Другой каталог можно
задать через `MACCHERI_FIXTURES=…`.

## Замеры в браузерах

```sh
node bench/latency.mjs --browser chrome --taps 40                         # /Applications/Google Chrome.app, дорожка
node bench/latency.mjs --browser chrome --steps measure:30,switch,wait:1500,measure:30   # оба режима в одной сессии
node bench/latency.mjs --browser chromium                                 # headless Chromium из кэша Playwright
safaridriver -p 4444 & node bench/latency.mjs --browser safari            # нужен `safaridriver --enable`
geckodriver -p 4444 & node bench/latency.mjs --browser firefox --url https://<IP>:5173/   # https, см. выше
```

Скрипт входит, создаёт сессию, кликает мышью браузера в центр экрана (TapProbe меняет цвет) и печатает
`RESULT … p50 … p95`. Параметр `--steps` вместо кликов выполняет проверки по шагам, например
`--steps home,shot:a,rotate:landscapeLeft,type:hi,install:/path/App.zip,button:Блокировка экрана,shot:b`.
Цифры собраны в `bench/simstream/RESULTS.md`.

## Чек-лист сквозного прогона

Нужен control plane с HTTPS: браузер даёт WebCodecs только в secure context, то есть на
`https://` или `localhost`. Нужны также хост с агентом (или `simstream-peer`) и прогретая VM.

1. **Вход.** Открыть `https://<домен>/` и войти: в v1 ввести `MACCHERI_SHARED_TOKEN`, в v2 нажать
   «Войти через GitHub» и выбрать команду. Должен появиться список «Маки команды», в нём нужный
   хост «в сети» с `свободно ≥ 1`.
2. **Сессия.** Нажать «Новая сессия». Статусы «Ищем свободный Mac…» → «Готовим виртуальную машину…» →
   экран устройства. Записать, сколько секунд показал счётчик до экрана.
3. **Оверлей** (левый верхний угол):

   | Строка | Что смотреть |
   |---|---|
   | `напрямую (host ⇄ srflx, udp)` или `через TURN (…)` | тип соединения. «напрямую» — P2P: типы кандидатов `host`, `srflx` или `prflx`. «через TURN» — хотя бы с одной стороны кандидат `relay`, в скобках транспорт до TURN (`udp`, `tcp`, `tls`) |
   | `RTT … мс, до симулятора … мс` | RTT — ICE до хоста. «До симулятора» — ping по каналу через хост в гостя и обратно, должно быть ≈ RTT + 1–2 мс |
   | `… fps, … Мбит/с` | в простое 0 fps и около 0 Мбит/с, это норма: кадры идут только при изменениях. При прокрутке 30–60 fps, 1–6 Мбит/с. `потеряно кадров N` появляется только в режиме канала данных |
   | `клик → кадр X мс (p50, p95, n)` | главное число. Кликать в TapProbe или в любое место, которое сразу реагирует. В Настройках ответ приходит после отпускания, и замеров не будет. Ориентир в LAN — 20–30 мс, через интернет — плюс RTT |
   | `из них сервер p50` | часть в госте: касание → кадр отправлен, ≈ 15–20 мс. Если растёт она, дело в госте, а не в сети |
   | `видео: …` | какой режим сейчас работает. По умолчанию дорожка, кнопка «Видео: …» на панели переключает режим без переподключения |

4. **Возможности.** Проверить по очереди:
   - ⌂ — домой;
   - ⏻ — блокировка, разблокировать кнопкой ⌂;
   - ⟲ / ⟳ — поворот (в Safari на iPhone картинка встаёт ровно, домашний экран остаётся боком);
   - набор текста в поиске (физические клавиши, раскладка устройства);
   - перетащить `.zip` с `.app` в окно → статус «Запущено: <bundle id>».
5. **Конец.** Нажать «Завершить» → «Сессия завершена» и итог клик → кадр. Проверить, что на хосте
   VM погашена и сессия в control plane `ended`. Отдельно: закрыть вкладку посреди сессии — сессия
   должна закончиться сама (DELETE с `keepalive` и `bye`).
6. **Relay принудительно.** Открыть `https://<домен>/?relay=1` и пройти шаги 2–3: в оверлее должно
   быть «через TURN (relay ⇄ …)». Так проверяется coturn и цена relay по RTT и клик → кадр.
7. **Оба режима видео — обязательно** при прогоне через интернет. В одной сессии сделать по 30 кликов
   в TapProbe на дорожке, нажать «Видео: …» (замеры начнутся заново) и сделать ещё 30 на канале данных.
   Затем то же самое при потерях: на хосте `dnctl`/`pfctl` (1–3%, RTT +50 мс) или плохой хотспот. При потерях
   смотреть на артефакты: серые или зелёные блоки, «размазанные» области, замирание до ключевого кадра,
   рывки, строку `потеряно кадров` в оверлее (только канал данных).
8. **Что записать** в таблицу «Через интернет» в `bench/simstream/RESULTS.md`: дату, браузер и ОС
   клиента, сеть клиента (LAN, хотспот, оператор), тип соединения из оверлея, RTT, p50 и p95 клик → кадр
   для каждого режима, артефакты при потерях своими словами, время от «Новой сессии» до экрана.

Что-то не так — открыть консоль браузера (ошибки сигнализации и декодера пишутся туда) и лог хоста
(`host-peer: connected: direct|relay (…)`, раз в 5 с — кадры, Мбит/с, выброшенные кадры).
